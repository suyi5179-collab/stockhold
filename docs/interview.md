# stockhold 面试题

按「面试官真的会这么问」来写。每题先给一句话答案，再展开，最后是追问和答法。
答案都落在这个仓库的代码和实测数据上。源码位置写成「文件（锚点 `名字`）」，在教学模式的「面试题」标签页里会变成固定在某个 commit 上的 GitHub 行号链接。

> 关于数字：简历上那段经历里的数字是在公司生产环境里的结果，**不是这个仓库测出来的**。这个仓库只报告它自己在本机 LocalStack 上跑出来的数：并发测试、失败对照、1 vs 8 分片压测、窗口期测量、模拟流量的 SQL 结果。面试时两类数字要分开说。

## 项目概述

### 讲讲这个项目？（一分钟版）

**一句话答案：** 一个库存预留服务：下单时把库存占住，付款成功就确认，付款失败或超时就把库存还回去，任何并发下都不超卖；配一个给值班工程师用的死信重放工具。

**展开：**
- 链路：Flask API → DynamoDB 条件写（扣库存 + 写 hold 在一个事务里）→ SQS 延迟消息 → expire Lambda；付款事件走另一个 SQS 队列 → payments Lambda → 失败三次进 DLQ。
- 状态机只有四个状态：HELD 走一步到 CONFIRMED / RELEASED / EXPIRED，终态不能再动（`stockhold/states.py`，锚点 `state-machine`）。
- 过期是最终释放：延迟消息加每分钟一次的 sweeper，不用锁。
- 热门商品的库存拆成分片，压测里一个分片三成七的请求因为冲突放弃，八个分片几乎没有。
- DLQ 重放工具：搜索、对比、dry-run、只有 oncall 能重放、最多重放一次、每次都有审计。
- 每个保护都有一个开关，关掉以后测试会红：不带条件写多卖二十件，不检查状态多还七次。

**追问：** 最难的部分是什么？
答：让「最多一次」在每个入口都成立：客户端重试、SQS 重复投递、两个值班同时点重放。三处用的是同一个办法：条件写。见 [q08](problems.md#q08-重复的付款失败消息把库存还了七次典型)。

### 这个项目和你简历上那段经历是什么关系？

**一句话答案：** 简历上是我在公司做的生产系统；这个仓库是用 LocalStack 把同样的设计从零重写一遍，别人能跑、能读、能验证，数字只报仓库自己测出来的。

**展开：**
- 对应关系：reserve / confirm / release / expire 四个步骤和显式状态转移、条件写和版本号、并发 / 过期 / 重复消息 / 部分失败的测试、CDK、DLQ 和告警、重放工具、热点 key 分片、用 SQL 分析过期率调 hold 时长。
- 不一样：AWS 换成 LocalStack 4.9，X-Ray 换成 Jaeger，CloudWatch 换成 Prometheus + Grafana，Athena 换成 DuckDB。
- 所以简历上的流量和比例不会出现在这里。这里能说的是「三十个人抢十件零超卖、对照组多卖二十件」这类仓库数字。

**追问：** 简历上说 flash sale 没有限流，你在这里能证明吗？
答：不能，而且 README 里写明了。LocalStack 不模拟分区限流。这里能实测的是同一行上乐观并发的冲突和尾延迟，见「扩展」里的分片题。

## 设计取舍

### 为什么用条件写，不用锁？

**一句话答案：** 扣库存是单行上的「读到的值还没变才写」，DynamoDB 的条件写原子地做了这件事，不需要另外的锁服务，也没有锁过期和锁泄漏的问题。

**展开：**
- reserve 是一个 `TransactWriteItems`：库存行 `available >= :n AND version = :v`，hold 行 `attribute_not_exists(PK)`（`stockhold/inventory.py`，锚点 `reserve-transact`）。
- 冲突了就重读重试，次数记在 hold 的 `reserve.conflicts` 里。
- 锁要解决「持有者挂了怎么办」，条件写没有持有者。
- 代价是热点行上的冲突重试，所以有了分片。

**追问：** `available >= :n` 已经是原子的了，为什么还要 version？
答：单看扣减确实够了。version 让「我读到的这一版」成为条件的一部分：后面要按读到的值做计算再写（比如分片之间挪库存），都靠它防丢失更新。代价是冲突更多，压测里看得到。

### 为什么是最终释放，而不是同步检查过期？

**一句话答案：** 同步检查会让每次读库存都变成写，热门商品上全是冲突；最终释放只多出一个可测量的窗口期，而窗口期里不会卖错，只会少卖一会儿。

**展开：**
- 设计文档 [docs/design.md](design.md) 第一节有完整的对比表。
- 窗口期里 confirm 的条件有 `expires_at_ms > :now`，过期了就是 `HOLD_EXPIRED`（锚点 `transition-guard`）。
- 实测窗口：Lambda 热的时候 p50 2478 毫秒、最大 3981 毫秒；模拟流量那一轮各商品 p50 一秒左右。
- 最坏情况：延迟消息和 expire Lambda 都失败，sweeper 每分钟兜底，上限约「五秒宽限 + 一分钟」。

**追问：** SQS 延迟最长十五分钟，hold 要三十分钟怎么办？
答：handler 看到还没到期就再投一条，`rescheduled`，一跳一跳接力（锚点 `expire-handler`）；sweeper 也会兜底。

### 为什么 hold id 从 Idempotency-Key 算出来？

**一句话答案：** 这样重试的请求天然落在同一行上，「已存在」就是幂等的判据，不需要单独的幂等表。

**展开：**
- `hold_id = sha256(client, key)`，按调用方隔离，两个商店都可以用 key「1」（`stockhold/keys.py`）。
- 同 key 同请求体返回原来的 hold（200，`replayed: true`），同 key 不同请求体是 422（锚点 `idempotent-replay`）。
- reserve 第一件事就是按 key 查，卖光以后的重试也能拿回自己的 hold。

**追问：** 请求体怎么比？
答：存一个 `request_hash = sha256([sku, qty, order_id])`。只比影响结果的字段，客户端多带的无关字段不算不同。

### 为什么单表设计？键是怎么定的？

**一句话答案：** 访问模式都很固定（按商品读分片、按 hold id 读写、扫过期的 hold、按商品列 hold），单表加两个 GSI 都能一次查询完成。

**展开：**
- 商品 `SKU#<sku> / META`，分片 `SKU#<sku> / SHARD#<k>`，hold `HOLD#<id> / HOLD`。
- GSI1 稀疏：只有 HELD 的 hold 有 `gsi1pk`，sweeper 只读开着的 hold；分成四个桶，避免「所有开着的 hold」变成一个热分区。
- GSI2 按商品查 hold，也按分片拆成 `SKU#<sku>#<k>`，不然热点只是从库存行搬到了索引上（锚点 `cdk-table`）。

**追问：** 为什么 GSI 也要考虑热点？
答：GSI 的写入是基表写入异步复制过去的，GSI 分区被限流会反压基表写入。秒杀商品所有 hold 写同一个 GSI 分区键，就是同一个热点。

### 为什么重放工具要先「归档」，不直接读 DLQ？

**一句话答案：** SQS 不能「看一眼」，receive 会改接收次数还会把消息藏起来；先搬进 DynamoDB，搜索、对比、审计都在归档上做。

**展开：**
- `sync()` 写归档成功以后才删 SQS 里那一份，中间崩了下次再归档是空操作（锚点 `dlq-archive`）。
- Flask 后台线程每三秒同步一次，告警是秒级新鲜。
- 搜索支持 hold id、sku、message id、原文、原因、状态、时间（锚点 `dlq-search`）。

**追问：** 归档放在一个分区里，量大怎么办？
答：现在是一个 `DLQ` 分区按时间排序，死信量小的时候最简单。量大了按日期分桶（`DLQ#<日期>`），搜索改成按时间范围查桶，或者把归档同时写进 S3 用 SQL 查。

### 为什么 DuckDB？和 Athena 什么关系？

**一句话答案：** 同样的 SQL、同样的 JSON Lines、同样按日期分区，AWS 上交给 Athena，本地交给 DuckDB。

**展开：**
- Streams → eventlog Lambda → `s3://stockhold-events/events/dt=…/hour=…/*.jsonl`（锚点 `stream-to-event`）。
- DuckDB `read_json_auto` 加 `hive_partitioning` 读本地镜像（锚点 `duckdb-view`）。
- 四条 SQL：过期率释放率（锚点 `sql-rates`）、付款等待分布、hold 时长建议（锚点 `sql-recommend`）、释放窗口。

**追问：** 建议值怎么算的，靠谱吗？
答：付款等待的 p99 乘 1.2。模拟数据里杯子 p99 7.3 秒建议 9 秒，球鞋 p99 18.5 秒建议 23 秒。它只说明链路能算出答案；真实商店要用真实事件，还要看过期带来的损失和占库存的损失哪个大。

### 重放工具为什么用 Flask 加原生 JavaScript，不用 React？

**一句话答案：** 这是给值班工程师的内部工具，页面少、交互简单，服务端渲染加几百行原生 JS 最容易维护，也和简历上那段经历的技术栈一致。

**展开：**
- 页面由 Jinja 模板出，数据走同源的 JSON 接口，会话用签名 cookie（`stockhold/ops.py`）。
- 三个页面（重放工具、结账模拟、教学模式）没有构建步骤，改完刷新就行。
- 所有危险动作在服务端校验角色，前端禁用按钮只是提示。

**追问：** 鉴权怎么做的？
答：API 用 JWT（HS256，一小时过期），页面用会话 cookie，同一个装饰器检查两种来源和角色（锚点 `require-role`）。测试覆盖了没 token、伪造 token、角色不对三种（锚点 `test-auth`）。

## 正确性和故障

### 两个人同时抢最后一件会怎样？

**一句话答案：** 两个事务的条件都是 `available >= 1 AND version = v`，只有一个能提交，另一个重读后看到没货，返回 409 INSUFFICIENT_STOCK。

**展开：**
- `tests/test_reserve.py::test_concurrent_checkouts_never_oversell`（锚点 `test-oversell`）：三十个线程抢十件，正好十个占到，库存恒等式成立。
- 冲突太多重试十二次还没成功的，返回 503 CONTENTION，客户端用同一个 key 重试是安全的。

**追问：** 503 的时候库存其实还有，用户体验不好怎么办？
答：一是分片（第六章），二是客户端带同一个 key 退避重试。模拟器就是这么做的（第七章踩过：不重试的版本有五十个请求直接报错）。

### 同一条付款失败的消息来了八次会怎样？

**一句话答案：** 只有一次真正释放，其余七次是 `changed: false` 的空操作。

**展开：**
- release 的条件是 `status = HELD AND version = :v`，和「还库存」在同一个事务里（锚点 `transition-guard`、`release-transact`）。
- 输掉的一方重读，看到已经是 RELEASED，就当成功返回，所以不会被当成失败去重试。
- 关掉保护：五件的商品变成十九件（锚点 `test-duplicate-release`，见 [q08](problems.md)）。

**追问：** 为什么不用一个「已处理消息 id」表去重？
答：业务状态本身就是去重键：hold 只能离开 HELD 一次。单独的去重表要和业务写放在同一个事务里才有意义，而状态条件已经做到了。

### reserve 提交了，延迟消息没发出去，进程就挂了，怎么办？

**一句话答案：** 两道兜底：同一个请求重试时补发；没人重试的话 sweeper 过期它。

**展开：**
- API 发现 hold 没有 `expiry_message` 就补发（锚点 `api-schedule`）。
- sweeper 扫 GSI1 里过期超过五秒的 hold（锚点 `sweeper`）。
- `test_sweeper_expires_a_hold_whose_message_was_lost`（锚点 `test-sweeper`）专门不发消息来验证。
- 反过来「扣了库存没写 hold」不可能出现，因为它们在同一个事务里。

**追问：** 为什么不先发消息再写库？
答：先发消息、写库失败，会留下一条指向不存在 hold 的消息；handler 会返回 `missing`，无害。两种顺序都能做对，我选了「先写库」，让 hold 先存在、消息后到。

### 付款晚到，hold 已经过期了会怎样？

**一句话答案：** confirm 的条件里有过期时间，确认不了，付款事件重试三次进死信，dry-run 提示「去退款，不是重放」。

**展开：**
- 这在第七章的突发流量里真实发生过：三十九条付款事件因为 `HOLD_EXPIRED` 进了死信（[q04](problems.md)）。
- dry-run 是纯函数，只读不写，告诉值班「会发生什么」或者「为什么不能」（锚点 `dry-run`）。

**追问：** 要不要在这种情况下自动把 hold 复活？
答：不要。过期以后库存可能已经卖给别人了，复活就是超卖。应该走退款，或者重新下单。

### 下游挂了，消息进了死信，恢复以后怎么处理？

**一句话答案：** 在重放工具里搜到它、看三次失败的原因、dry-run、重放；重放最多一次，重放出去的消息照样走幂等的 release。

**展开：**
- 重放前重新算一次计划，dry-run 和点击之间状态可能变了。
- 认领是条件写：归档行 `OPEN → REPLAYING`，五个人同时点只有一个成功（锚点 `replay`）。
- 只有 oncall 角色能重放，viewer 能看能 dry-run（锚点 `require-role`、`replay-endpoint`）。
- 测试：五个线程同时重放，结果 `[200, 409, 409, 409, 409]`，库存只回来一次（锚点 `test-replay-safety`）。

**追问：** 畸形消息能重放吗？
答：不能，dry-run 直接说「修生产方，重放没有用」。重放只解决「当时下游不可用」这类临时问题。

### 怎么知道死信在堆积？

**一句话答案：** 两个告警：死信里最老的那条超过五分钟，十五分钟内进死信五条以上；重放工具顶部和 Prometheus 规则用的是同一套阈值。

**展开：**
- 工具顶部：`DLQOldestMessageAge`、`DLQRedriveVolume`（锚点 `alerts`）。
- Prometheus 规则还多两条：超卖大于零、过期了没释放的 hold 持续两分钟（锚点 `alert-rules`）。

**追问：** 「几分钟内能看到」是怎么保证的？
答：后台每三秒归档一次，Prometheus 每五秒抓一次，告警评估五秒一次。最慢的一环是 `for: 1m`，所以是一分钟量级。

## 扩展

### 流量放大十倍、一百倍，瓶颈在哪？

**一句话答案：** 先是热门商品的库存行（同一个分区键上的写），然后是付款事件的消费速度，最后是重放工具的单分区归档。

**展开：**
- 热门商品：分片数随峰值调，`split_stock` 均分（锚点 `flash-sale`）。
- 消费：Lambda 的并发跟着队列深度扩，批内并行（锚点 `payments-batch`）；第七章在本机上看到的十秒排队，是 LocalStack 单个 poller 和本机 DynamoDB 饱和造成的。
- 归档：按日期分桶。
- sweeper：GSI1 已经分了四个桶，可以按桶并行扫。

**追问：** 一百倍的时候分片要多少？
答：按「单分区每秒写入上限 / 每单的写入数」算出单片能扛的 TPS，再除峰值。还要看每单件数：一单必须从一个分片里拿够，分片太多会出现「总数够、单片不够」（`test_an_order_must_fit_in_one_shard`）。

### 1 个分片和 8 个分片，实测差多少？

**一句话答案：** 400 件、400 单、32 并发，三轮：1 个分片每轮约 148 单冲突放弃、每单平均冲突 4.2～4.3 次；8 个分片放弃 0～1 单、每单冲突 1.5～1.6 次，零超卖两边都成立。

**展开：**
- `scripts/bench_shards.py`，原始输出 `docs/results/bench_shards.md`。
- p99 1 个分片 2.4～4.3 秒，8 个分片 1.4～3.1 秒；本机 LocalStack 抖动很大，只看相对变化。
- 没有测「限流」，LocalStack 不模拟它。

**追问：** 冲突重试为什么不用 SDK 自带的重试？
答：DynamoDB 客户端把 SDK 重试关掉了（`max_attempts: 1`），冲突由自己的循环重试，这样冲突次数才能被数出来、写进 hold、进指标。

### 卖到最后几件，分片会有什么问题？

**一句话答案：** 库存散在各个分片里，每片都只剩零星几件，大一点的单拿不到，随机选分片也会多试几次。

**展开：**
- 测试里八件分八片，卖掉四件以后，想一次买两件就买不到，虽然总数还有四件。
- 改进办法：剩余量低于阈值时合并回一个分片，或者 reserve 时优先选剩余多的分片。这里没有实现，写在 README 的局限里。

**追问：** 合并的时候会不会超卖？
答：合并要把「从 A 片减、往 B 片加」放进一个事务，两边都带 version 条件；和 reserve 同样的保证。

## 测试

### 你怎么证明它是对的？

**一句话答案：** 并发、过期、重复消息、部分失败、重放安全各有集成测试，打的是真的 LocalStack；关键的两个保护各有一个开关，关掉以后对应测试必须变红。

**展开：**
- 共 67 个测试（单元 + 集成），覆盖率见 README。
- 集成测试走真的 SQS 和 Lambda 容器：延迟消息过期、毒消息三次后进死信并带原因、重复付款事件只释放一次、事件进 S3、一条 trace 穿过队列。
- Playwright 从界面点一遍教学模式、重放工具和结账页。

**追问：** 为什么要失败对照？
答：绿的测试可能什么都没测。我见过「断言终态」的并发测试在关掉保护后照样绿。对照组证明判据是活的：不带条件写，三十个人抢十件，测试报 `assert 20 == 0`。

### 失败对照是怎么设计的？

**一句话答案：** 环境变量 `STOCKHOLD_SABOTAGE` 切换到「显而易见但错误」的写法：`no_condition` 走不带条件的读改写，`no_release_guard` 走两次不带条件的写。

**展开：**
- 两条错误路径在代码里有锚点（`reserve-unsafe`、`release-unsafe`），也是问题视频里「修复前」的代码。
- `_reserve_unsafe` 在读和写之间留了两毫秒，模拟真实读改写的间隙，让竞争稳定复现。
- 输出原样贴在 README 里：打开保护绿、关掉保护红，两次都贴。

**追问：** 对照只在进程内生效，Lambda 里呢？
答：开关是进程环境变量，测试在进程内调核心函数，所以对照覆盖的是核心逻辑，不是部署后的 Lambda。Lambda 跑的是同一份代码（`scripts/build_lambda.sh` 直接拷 `stockhold/`）。

## 系统设计延伸

### 一条请求穿过队列以后，怎么还能在一个 trace 里看到？

**一句话答案：** 发消息时把 W3C `traceparent` 写进 SQS 的 message attribute，Lambda 收到以后把它当父 span；Lambda 里没有 OTel SDK，就用一个手写的 OTLP/HTTP JSON 发送器。

**展开：**
- Flask 里每个请求一个 span（锚点 `request-span`），核心代码只写 `with tracing.span(...)`。
- Jaeger 里同一个 trace：`POST /learn/api/start` → `inventory.reserve` → `payment.webhook` → `payments.handle` → `hold.transition`。
- 测试断言同一个 trace 里同时有 API 和 payments 两个服务（锚点 `test-trace-e2e`）。

**追问：** 教学页面的「看源码」链接为什么不写死 main 分支？
答：main 会变，行号会漂。链接用当前 commit 的 sha 和脚本生成的行号拼出来（锚点 `source-url`），CI 里检查每个锚点都存在、行号在文件范围内、生成文件没过期。

### 上生产还缺什么？

**一句话答案：** 真正的身份和密钥管理、多区域、真实的支付回调签名校验、限流、退款流程、数据保留策略，以及在真 AWS 上重新量所有数字。

**展开：**
- JWT 密钥现在是环境变量里的 dev 占位值，生产要放 Secrets Manager 并轮换。
- 付款 webhook 要校验签名、防重放。
- 告警要接到 PagerDuty 之类，带 runbook 链接到重放工具。
- 合并分片、hold 时长按商品自动调整，都还没做。

**追问：** 换成真 AWS 要改哪些代码？
答：几乎不改：boto3 不设 `AWS_ENDPOINT_URL` 就走真 AWS；CDK 栈去掉 cdklocal 直接 `cdk deploy`；Jaeger 换 X-Ray（OTel 有 X-Ray exporter）；Prometheus 换 CloudWatch EMF；DuckDB 换 Athena 建外部表。

### 换成真的 AWS，哪些结论会变？

**一句话答案：** 正确性结论不变（条件写的语义一样），性能结论全部要重测：延迟、窗口期、分片的收益在 AWS 上都会不同。

**展开：**
- 窗口期：真 SQS 长轮询，ESM 会扩多个 poller，第七章的十秒排队大概率不存在。
- 分片：真 DynamoDB 有分区限流，分片的收益会比本地更大，也更需要。
- LocalStack 和 AWS 的差异已经踩过两个：Stream 加不到已有的表上、ESM 空轮询退避。

**追问：** 那本地测出来的数有什么用？
答：证明机制是对的、测试是活的，以及给出相对比较（1 对 8 分片）。绝对值不能拿去做容量规划。

## 简历对应

### 简历写「zero oversells」，面试官追问你怎么保证？

**一句话答案：** 条件写加版本号，在仓库里有对照：同一个测试打开保护零超卖，关掉保护多卖二十件。

**展开：**
- 讲设计：`available >= :n AND version = :v` 和 hold 的 `attribute_not_exists` 放在一个事务里。
- 讲证明：对照组、恒等式 `available + held + confirmed == capacity`、Prometheus 的超卖告警恒为零。
- 简历上的生产结果是公司里的；仓库里的数字是本机并发测试的，分开说。

**追问：** 如果有人绕过 API 直接改库存呢？
答：那就破坏了恒等式。`stock_report` 会算出 `balanced: false`，指标和告警能看到；生产上要靠 IAM 只让服务角色写这张表。

### 简历写「eventual release instead of synchronous locks」，怎么追问？

**一句话答案：** 会问窗口期多大、最坏情况、为什么可以接受；仓库里都有实测和文档。

**展开：**
- 窗口期本机实测：热 Lambda 下 p50 2.5 秒、最大 4 秒；模拟流量里各商品 p50 一秒左右。
- 最坏情况：sweeper 每分钟兜底。
- 为什么可以接受：窗口期里只是少卖，不会卖错；confirm 带过期条件。

**追问：** 你们生产上的窗口期是多少？
答：那是公司里的数据，我只讲这个仓库能复现的部分；量法是一样的（`scripts/measure_expiry_lag.py` 加第七章的 `release_window.sql`）。

### 简历写重放工具「search, compare, replay safely」，怎么用仓库回答？

**一句话答案：** 直接演示：故障演练造一条死信，十五秒后在工具里搜到，看三次失败，对比消息和当前 hold，dry-run，重放，再点一次被拒绝。

**展开：**
- e2e 测试从界面走完这一整套，包括 viewer 看不到重放按钮。
- 安全性的三层：重新计划、条件写认领、release 本身幂等。
- 审计：dry-run、重放、被拒绝的重放都有记录。

**追问：** 谁能重放、怎么防止误操作？
答：只有 oncall；先 dry-run 看到「会发生什么」；重放最多一次；不允许的情况（畸形、hold 不在、已终态）根本点不成。
